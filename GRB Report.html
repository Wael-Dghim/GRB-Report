01Executive summary

GRB 2.0 already has most of what a migration target needs:

  • a national reference data schema;
  • per-domain schemas (recette, document, utilisateur, history);
  • Liquibase-managed DDL;
  • tables built to receive legacy data. SITUATION_ARTICLE and LIGNE_SITUATION_ARTICLE carry an etat_reprise (migration status) flag, an ancien_code field and legacy-style amount columns.

What is missing is a repeatable migration capability. There is no documented migration process, no ETL tooling, no reconciliation procedure and no sign-off model. Several target constraints will also block national rollout as currently designed.

24governorates
350communes
86communes created 2015–2016
187communes territorially extended

Legacy data for the newly created and extended communes may still sit under another commune's codes. Some migrations will therefore require re-attributing articles by address or sector, not just copying them.

Recommendation. Treat the next municipality as a pilot for a migration factory, not a one-off. In order:
  1. Fix the blocking constraints.
  2. Build a staging schema with crosswalk tables, plus a validation and reconciliation suite.
  3. Run the pilot with at least two full rehearsals.
  4. Migrate the rest in waves grouped by recette des finances and by source-system type.
The unit of migration should be the recette, not the single municipality. That avoids a revenue office working in two systems at once.

02Scope and context

Migrating a municipality covers four layers, each of which must be live and consistent at cutover.

LayerContent
Reference dataGovernorate, municipality, arrondissements, sectors, attached recette, municipal tariffs, services, infraction types, banks
Users and accessMunicipal and recette staff in Keycloak and the utilisateur schema, scoped to municipality/arrondissement/sector/recette
Business dataTax articles and their per-year situations, contracts and amendments, schedules, licences, fines, annual rolls, titres
Financial historyOpen balances (restes), payments, quittances, closed journals, according to the cut-off policy chosen (§13)

Actors

  • The municipality is the data owner for assessments, contracts, licences and fines.
  • The recette des finances is accountable for collection balances.
  • The Ministry of the Interior and Ministry of Finance are the sponsors.
  • CNI is the likely host and operator of legacy systems.
  • GIZ chairs the steering committee.
  • think tank Business Solutions is the platform vendor.
  • The migration team (us) runs the migration.

Assumptions

  • The source can be anything: a legacy national application, a local application, spreadsheets or partial paper records. The approach below doesn't depend on knowing the source.
  • At least one municipality has already been loaded. The wording "another municipality" and the presence of reprise tables suggest this. Its scripts are the single most valuable input we can obtain (§13).

05Gaps and risks to resolve before migrating

Blocking

Globally unique names

uk_municipalite_libelle, uk_arrondissement_libelle and uk_secteur_libelle enforce uniqueness across the country. Generic names like "Centre-ville" or "Secteur 1" will collide almost immediately. Change these to composite uniqueness (parent ID + name).

Blocking

No commune code in the reference data

Articles, situations and the public API key on code_commune, but municipalite exposes no such field. Add an official commune code column with a unique constraint. This also fixes the public API gap.

Blocking

One licence per CIN

uc_licence_cin_beneficiaire means a person can hold only one licence ever. Real data will violate this. Drop it or replace it with a business-correct rule.

Blocking

Payment-mode mismatch

The article.mode_paiement CHECK allows ESPECE, CHEQUE, VIREMENT, VIREMENT_INTERN and TPE. The API enum has VIREMENT_POSTAL, VIREMENT_BANCAIRE and PAIEMENT_ELECTRONIQUE. Legacy and electronic payments will fail on insert.

Blocking

Data loaded via Liquibase

Per-municipality data in schema changelogs runs at application startup, lives in the code repository, mixes reference data with transactional data and can't be re-run or rolled back per municipality. Move data loading to a dedicated ETL.

High

Money precision

Most amounts are numeric(18,3), which is correct for millimes. But contravention uses (19,2) and paiement_transaction uses (10,3). The API mixes string and number types. Standardise before loading.

High

Field-length mismatches

code_article is varchar(50) in ARTICLE but varchar(16) in situation and transaction tables, and numeric in role_annuel. transaction_id is 50 in the database vs 100 in the API. code_redevable is varchar(10) and NOT NULL. Legacy codes may not fit.

High

Documentation drift

The column documentation differs from the DDL: cin and matricule_fiscal on article, cin and article_id on certificat_decharge. Work from a schema dump of the actual target environment, not from the documents.

High

Two article models

It's unclear whether liquidation and the public API read ARTICLE or SITUATION_ARTICLE. Loading both inconsistently would show citizens wrong balances.

High

Mandatory fields legacy data may lack

type_identifiant, source, etat_article and code_arrondissement are NOT NULL with closed value lists. Each one needs an explicit default rule agreed with the business.

High

Testing

H2 can't validate PostgreSQL CHECKs, arrays, views or sequences. Migration rehearsals need a real PostgreSQL 17 (Testcontainers or a staging copy).

Medium

Sequences

echeance and adresse have no default nextval. Explicit-ID inserts require resetting sequences afterwards.

Medium

Encoding

Arabic names and addresses in legacy systems are often stored in Windows-1256 or older encodings. Convert to UTF-8 and verify visually on samples.

Medium

Privacy

Migrated taxpayer data becomes reachable through the public article endpoint using code article + commune. Check whether article codes are guessable, and align with the national data-protection authority's requirements.

06What we need from each municipality

Send this discovery request before any technical work.

Systems and data

  • Inventory of systems in use per domain (tax articles, rolls, leases, licences, fines, receipts), with vendor and version
  • Database access or a full dump, plus the schema, code tables and any data dictionary
  • Code lists: commune, arrondissement, sector, street types, tax types, statuses, payment modes, nomenclature codes
  • Volumes per domain and per year: articles, lines, contracts, licences, fines, quittances

Balances and quality

  • Current open balances per tax type and year, as reported by the recette. This is the reference for reconciliation
  • Known data issues: duplicate taxpayers, missing identifiers, disputed articles, amnesty cases
  • For communes created or extended in 2015–2016: which records are still held by the "parent" commune

People

  • Staff list with roles and scope, for user provisioning
  • Business contacts: a data owner in the municipality and an accountable person in the recette (the receveur)

Calendar

  • Payment peaks
  • Closing dates
  • Annual roll issuance

07Migration approach — per-municipality playbook

  • Preconditions (once, before the pilot)

    Fix the §5 blockers; build the staging schema, crosswalk tables, validation and reconciliation suite, user provisioning script; get a schema dump of production.
    Exit: factory tooling tested on synthetic data

  • Discovery

    Send the §6 request; profile source data (counts, null rates, value distributions, duplicates, encoding).
    Exit: data profile report; volumes known

  • Mapping

    Field-by-field mapping spec source → staging → target; value mappings for every enum; default rules for missing mandatory fields.
    Exit: mapping spec signed by the municipality and the recette

  • Build

    Extract to staging; transform; load in dependency order: reference data → users → addresses → articles/situations → contracts → schedules → licences → fines → payments/quittances.
    Exit: full load runs end-to-end without constraint errors

  • Rehearsal 1

    Full load on a copy of the target; run all §9 controls; business users test in the UI and via liquidation.
    Exit: defect list; data-quality issues triaged

  • Data cleansing

    The municipality and recette fix source data or approve transformation rules.
    Exit: issues closed or formally accepted

  • Rehearsal 2 (dress rehearsal)

    Timed full run with the cutover runbook.
    Exit: reconciliation within tolerance; timings fit the cutover window

  • Cutover

    See §10.
    Exit: signed go-live record

  • Hypercare (2–4 weeks)

    Daily reconciliation of collections; support for staff.
    Exit: stable; handover to run teams

08Mapping and transformation rules

Template columns for the mapping spec: source table · source field · type/length · sample values · target table · target field · transformation rule · default if null · validation rule · owner · status.

Rules known now

TopicRule
CodesKeep commune, article and taxpayer codes as text and preserve leading zeros. Spreadsheet sources often strip them.
MoneyConvert to TND with 3 decimals. If the source stores millimes as integers, divide by 1,000. Never pass amounts through floating point.
EnumsEvery source value maps explicitly to a target value. An unmapped value stops the load; it is never defaulted silently.
IdentityCIN is 8 characters (pad with zeros). Normalise and validate the tax ID format. Deduplicate taxpayers within the municipality before loading and record merges in a crosswalk.
AddressesMap street types to the reference table and keep the raw address text alongside the structured fields.
KeysGenerate UUIDs in staging and store a crosswalk (source ID ↔ target ID ↔ UUID) per object. This lets loads be re-run, makes reconciliation possible and supports later corrections.
TraceabilitySet creator = 'MIG_<commune>_<run>', version = 0 and deleted = false on every migrated row. Write one activity_history entry per batch, since bulk loads emit no events. Set etat_reprise on situation rows according to its documented meaning (to confirm with think tank).
Load methodLoad set-based through staging with target constraints active, not through the REST services. Services would be slow and would flood RabbitMQ. The trade-off is that business computations in the services won't run, so any derived amount must be reproduced and checked.

Formal sign-off. The reconciliation report becomes a balance-transfer record (procès-verbal de reprise des soldes), signed by the municipality and the receveur. Without it, the recette takes on balances it can't vouch for.

10Cutover and go-live

StepDetails
TimingSchedule the cutover after a daily journal closure, ideally over a weekend. Avoid year-end closing, annual roll issuance and known payment peaks. Since we are now in November, a cutover before year-end carries extra risk.
FreezeStop entries in the legacy system for the municipality, and for its whole recette if wave-based. Take a final extract and load any final changes.
Go/no-goAll §9 controls pass, users are provisioned, and the public API is checked on samples.
After go-liveSet the legacy system to read-only for the migrated scope to prevent double collection. Keep it accessible for consultation.
RollbackUse a pre-load database snapshot. Rows tagged MIG_<commune>_<run> can also be removed selectively, provided no live transaction has touched them yet. Define the point of no return, typically the first live quittance.

11Scaling to all remaining municipalities

Migration factory

Build once, reuse for every migration:

  • staging schema and crosswalk;
  • per-source-system mapping packs;
  • validation and reconciliation suite;
  • user provisioning;
  • cutover runbook template;
  • per-municipality dossier template.

The second municipality on the same source system should cost a fraction of the first.

Wave design

Unit = recette des finances

One recette serves several municipalities (municipalite.recette_id). Migrating them together avoids a revenue office working in two systems at once.

Group by source system

Municipalities on the same legacy application share a mapping pack.

Sequence

  1. Pilot (the next municipality).
  2. A small wave on the same source system to industrialise.
  3. Larger waves.
  4. The 2015–2016 new and extended communes last, or as a dedicated stream, because of re-attribution work.

Effort drivers to size each wave: source-system type, number of articles and contracts, data-quality score from profiling, number of domains in use, and whether data must be re-attributed between communes. Use a scoring grid filled in during discovery rather than fixed estimates now.

13Open questions and decisions needed

  1. Which municipalities are already on GRB 2.0, and can we get the scripts and lessons from their migration?
  2. Which model is the source of truth for tax balances, ARTICLE or SITUATION_ARTICLE, and what does etat_reprise mean exactly?
  3. What do amounts 1, 2 and 3 in the situation tables correspond to (principal tax, FNAH, other)?
  4. History cut-off: open balances only, or open balances plus payment history for the legal prescription period? This needs confirmation from the Ministry of Finance.
  5. Should payment schedules for existing contracts be migrated or regenerated by GRB?
  6. Should scanned documents be migrated, and where should they be stored (bytea vs object storage)?
  7. Who owns the §5 fixes, and on what timeline? They gate the pilot.
  8. Is there one dominant legacy application across municipalities? This largely decides the factory's economics.
  9. How will user credentials be distributed and trained per wave?
  10. What privacy requirements apply to public lookup of migrated taxpayer data?
